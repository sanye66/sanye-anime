## 1. 计划结论

单人开发不适合同时建设完整微服务体系、复杂管理平台和所有 AI 能力。当前计划采用以下策略：

1. 产品范围收缩到 PC Web MVP。
2. 后端按微服务拆分（`sanye_gateway` + 八个业务服务 + RuoYi 管理端，见决策 D-024），服务间通过 OpenFeign 与事件协作；前端（`sanye_client` 客户端+官网、`sanye_admin`）与全部工程纳入首版（D-025），统一经网关对接。
3. 正式编码前依次完成原型评审、页面状态、MVP 冻结、管理平台原型、产品文档、技术设计和任务拆分。
4. 通过前置门禁后，先打通一条“首页 -> 作品详情 -> AI 提问 -> 推荐卡片”的垂直链路。
5. 测试、代码检查、依赖扫描、备份和日志从正式编码第一周建立。
6. RuoYi、RabbitMQ、XXL-JOB、Elasticsearch 和 MinIO 采用最小可用接入，复杂能力延后。
7. 版本基线以 [version-baseline.md](./version-baseline.md) 为准。
8. 三叶桌宠作为客户端 P1 增量，核心 PC Web MVP 稳定后再进入实现。

原先按多人团队估算的阶段人日不适用于单人开发。本计划的核心 MVP 按 113 至 115 个有效工作日估算（微服务与前端重新基线，D-024/D-025），其中正式编码前置门禁占 8 至 10 个工作日；再预留 2 至 4 周处理返工和外部依赖，形成约 26 至 30 周日历工期。

## 2. 单人开发前提

### 2.1 资源假设

| 角色 | 参与方式 |
| --- | --- |
| 开发者 | 负责产品落地、客户端、服务端、测试和发布 |
| 产品决策 | 由开发者依据产品文档做决定，重大变更记录在决策清单 |
| UI 设计 | 先使用现有产品文档和低保真原型，必要时外部评审 |
| 测试 | 自动化测试 + 手工验收 + 发布前外部体验 |
| 运维 | 采用 Docker 和脚本化操作，复杂生产环境暂不引入 |

### 2.2 技术前提

- PC 客户端首版按 PC Web 开发，不提前引入 Electron。
- Java 服务使用版本基线中的 Spring Cloud Alibaba 体系。
- 业务代码采用一个核心应用，内部按用户、动漫、搜索、AI、文件、反馈和任务模块划分。
- RuoYi 管理平台保持独立，不强行合并到核心应用的父工程。
- AI 使用第三方模型，不包含模型训练。
- 开发阶段使用内部测试数据；动漫数据、图片和外部跳转的正式授权以 [gap-register.md](./gap-register.md) 中的外部门禁为准。
- 首版不做语音、图片识番、会员支付、多人聊天室和长期角色陪伴。
- 桌宠首版只做 Windows 轻量桌面伴侣，不做复杂养成、语音通话、多角色和重型三维。

### 2.3 已冻结事项与外部门禁

以下事项已经按 [decision-log.md](./decision-log.md) 冻结，不再阻塞文档、原型评审和工程骨架维护；正式业务编码仍须通过第 7 节定义的前置门禁：

- 首版采用 PC Web，Windows 优先，不提前引入 Electron。
- 后端首版按微服务架构建设（`sanye_gateway` + 八个业务服务 + RuoYi 管理端，见决策 D-024）；三个核心工程按 Spring、Vue 和 RuoYi 技术边界建设。
- 官网首版只提供公开入口、产品介绍、法律信息和必要的公开内容，页面归入 `sanye_client`，不复制完整 AI 工作区。
- 管理平台独立运行，普通用户和运营人员使用不同权限边界。

以下事项仍是外部门禁，不能仅靠文档完成：

- 动漫数据、图片和外部链接的授权范围。
- AI 模型供应商、调用额度、成本上限和服务协议。
- RuoYi、基础设施镜像和 Spring Cloud Alibaba 的实际兼容性。
- 正式部署环境、备份存储位置和生产安全扫描结果。

## 3. 企业级最低标准

单人开发可以减少流程人员，但不能省略质量控制。每次发布至少满足：

- 需求有版本和决策记录。
- 代码经过自动构建、测试和依赖扫描。
- 核心数据有备份和恢复验证。
- 生产配置、密钥和用户数据不进入 Git。
- 用户、会话、文件和管理操作有权限边界。
- AI 有固定评测问题集、剧透测试和安全测试。
- 发布有检查清单、回滚方案和已知问题。
- 关键运行指标可以查看，异常可以收到提醒。

## 4. 正确的开发顺序

```text
完整评审客户端与官网原型
  -> 补齐页面状态
  -> 冻结 MVP 范围
  -> 完成管理平台原型
  -> 固化 product 产品文档
  -> 完成 docs 技术设计
  -> 拆分开发任务并估时
  -> 进入正式业务代码开发
  -> 工程基础和自动化门禁
  -> 最小垂直链路验证
  -> 首页、作品和搜索
  -> AI 核心能力
  -> 账户、收藏和管理功能
  -> 持续测试、安全、备份和监控
  -> 预发布验收
  -> 灰度发布和复盘
```

正式业务代码开发不是当前流程的起点。只有原型、状态、范围和文档均达到可验收状态，技术方案与任务拆分才有稳定输入，之后才能创建具体的 `feature/<task>` 分支。

### 4.1 当前阶段

- 前置门禁 `PRE-TODO-001` 至 `PRE-TODO-008` 已全部关闭，正式业务代码、管理端联调和本地质量门禁均已完成；后续只推进外部环境门禁、发布验收和代码质量收口。
- 任务分支命名暂用 `feature-<task>`（历史 `feature` 分支存在导致 Git 不允许同名前缀，见 D-023），`feature` 分支归档后恢复 `feature/<task>`。

### 4.2 为什么先做垂直链路

AI 项目的最大风险不是页面数量，而是以下能力能否同时成立：

- PC 页面布局是否适合长时间聊天。
- 作品数据是否能支持准确推荐。
- AI 回答能否稳定流式展示。
- 推荐结果是否能回到真实作品详情。
- 模型成本是否可接受。

如果先花几周完成全部首页和管理功能，再发现 AI 链路不可用，返工成本会很高。因此第 6 周前必须完成一次可运行的端到端样板（与第 5 至 6 周垂直链路排期一致）。

阶段预算：8 至 10 个有效工作日。客户端和官网原型已经具备初始成果，预算仍包含完整评审、返工和冻结记录，不以“页面能打开”代替产品验收。

| 顺序 | 任务 | 具体工作 | 产出 | 阶段出口 |
| ---: | --- | --- | --- | --- |
| 1 | 完整评审原型 | 逐页评审客户端与官网的信息层级、导航、交互、中文文案、亮暗主题、可用性和视觉一致性 | 原型评审记录与问题清单 | 两个原型的主流程可连续操作，阻塞性页面问题全部有结论 |
| 2 | 补齐页面状态 | 为每个 P0 页面补齐默认、加载、空数据、失败、无权限、离线、提交中和完成状态，并明确状态之间的跳转 | 页面状态矩阵 | P0 页面不存在只能展示理想数据的单一状态 |
| 3 | 冻结 MVP 范围 | 将功能划分为 P0、P1、P2，明确本期不做内容、依赖、验收标准和变更规则 | MVP 冻结清单 | 每项首版功能均有优先级、验收描述和唯一归属平台 |
| 4 | 完成管理平台原型 | 完成 RuoYi 管理平台 P0 页面、导航、列表、表单、详情、反馈和权限可见性原型，并补齐关键状态 | 管理平台可交互原型 | 管理员可在原型中走通内容维护、反馈处理和基础运营流程 |
| 5 | 固化产品文档 | 将已确认的定位、用户场景、功能、页面、交互、状态和产品验收写入 `product/`，消除原型与文档冲突 | 产品文档冻结版本 | `product/` 能独立说明做什么、给谁用和如何验收，不包含 API、数据库或部署内容 |
| 6 | 开始技术设计 | 根据冻结产品范围，在 `docs/` 完成系统边界、模块职责、数据、权限、异常、安全、部署和测试设计 | 技术设计评审版本 | 每个 P0 功能都有明确技术归属，不存在阻塞开发的架构决策 |
| 7 | 拆分开发任务 | 按可独立开发、测试和验收的粒度拆分任务，标记依赖、风险、工期和完成定义 | 可执行任务清单与排期 | 每个任务原则上不超过 1 至 3 个有效工作日，且能够单独验收 |
| 8 | 进入正式代码开发 | 前七步全部通过后，按任务创建 `feature/<task>` 分支，从最小垂直链路开始实现 | 首个正式开发任务 | 分支、需求、设计、测试范围和验收标准相互对应 |

门禁规则：

- 任一步未达到阶段出口，后续步骤不得标记为完成。
- 产品内容只固化到 `product/`，技术设计、任务和实施证据只进入 `docs/`。
- 测试作品和图片必须可以合法使用，或明确标记为仅限内部原型与测试。
- AI 模型、额度、成本、安全边界，以及登录、收藏、会话和隐私规则，必须在技术设计完成前形成决策记录。
- 前七步未关闭前，不创建承载新业务功能的 `feature/<task>` 分支。

## 8. 阶段 B：工程基础和自动化门禁

阶段预算：10 个工作日。

### 8.1 仓库和分支

```text
feature/<task> -> dev -> test -> release
```

- `dev`：日常集成分支。
- `test`：验收分支，只接收已经自测通过的内容。
- `release`：稳定发布分支，作为当前生产基线。
- `feature/<task>`：短生命周期功能分支。
- 已存在的 `feature` 分支保留，但不作为日常直接开发分支。

单人开发没有同事进行代码评审，因此用以下方式替代：

- 所有功能从 `feature/<task>` 开始。
- 合并前至少等待一个独立检查周期，不边写边直接合并。
- 使用自动构建、测试、依赖扫描和密钥扫描。
- 合并前按清单自查权限、异常、日志和回滚。
- `release` 分支只接受已通过测试的提交。

### 8.2 自动检查门禁

每次推送和合并至少执行：

- Java 编译和单元测试。
- 前端构建、类型检查和代码规范检查。
- 依赖漏洞扫描。
- 敏感信息和密钥扫描。
- Docker 镜像构建检查。
- 数据库迁移在空库和升级库上的验证。

任何一项失败都不能进入 `test`。

### 8.3 本地环境

先启动开发必需组件：

- PostgreSQL。
- Redis。
- Elasticsearch。
- MinIO。

完成垂直链路后再接入：

- RabbitMQ 异步事件。
- XXL-JOB 排期同步。
- Nacos 配置和服务治理。
- Sentinel 限流和降级。

这样可以避免第一周同时排查八类基础设施问题。

## 9. 阶段 C：最小垂直链路

阶段预算：10 个工作日。

### 必须完成

1. PC 左侧导航和首页内容壳层。
2. 一个作品详情页。
3. AI 页面空状态和文本输入。
4. 一次真实或受控的 AI 问答。
5. AI 回答过程中的等待、成功、停止和失败。
6. 一个推荐作品卡片。
7. 从推荐卡片回到作品详情。

### 垂直链路出口

- 用户可以从首页进入作品详情。
- 用户可以从详情进入 AI。
- AI 可以回答一个动漫问题。
- 推荐结果可以回到作品详情。
- 失败时不会丢失用户问题。
- 这一链路可以在本地和测试环境重复运行。

## 10. 阶段 D：首页和内容

阶段预算：15 个工作日。

| 工作项 | 预计时间 |
| --- | ---: |
| 精选、日漫、剧场版分类 | 2d |
| Banner 和内容分区 | 3d |
| 作品卡片和详情页完善 | 3d |
| 搜索和搜索无结果引导 | 3d |
| 热度排行榜和番剧排期 | 2d |
| 首页空状态、加载和失败状态 | 2d |
| **合计** | **15d** |

阶段出口：

- 首页能够持续浏览，不依赖单个内容区成功。
- 搜索、详情、榜单和排期可以互相跳转。
- 内容图片失败不破坏布局。
- 下架、暂无排期和无搜索结果都有明确展示。

## 11. 阶段 E：AI 核心能力

阶段预算：20 个工作日。

| 工作项 | 预计时间 |
| --- | ---: |
| 会话创建、打开、删除和历史 | 3d |
| 文本输入、草稿、快捷问题 | 2d |
| 流式回答、停止、失败和重试 | 4d |
| 作品上下文和剧透模式 | 2d |
| 推荐作品卡片和详情承接 | 3d |
| 额度、匿名体验和登录引导 | 2d |
| 安全拒答和敏感场景 | 2d |
| AI 评测集和回归结果 | 2d |
| **P0 合计** | **20d** |

复制回答、回答反馈、会话归档和会话整理延后到 P1，P0 只保留问答、流式、停止、重试、推荐、剧透和历史基本能力。

### 11.1 AI 评测最低标准

建立至少 100 条固定问题：

- 推荐问题 25 条。
- 剧情问题 25 条。
- 角色问题 20 条。
- 观看顺序和排期问题 15 条。
- 安全拒答和剧透问题 15 条。

首版通过标准：

- 安全类问题不得出现明确违规输出。
- 剧透规则通过率不低于 95%。
- 作品引用准确率不低于 90%。
- 推荐结果中可打开的有效作品比例不低于 95%。
- 失败、超时和额度耗尽均能给出明确提示。

## 12. 阶段 F：账户、管理和任务

阶段预算：12 个工作日。

### P0 首版必须功能

- 登录和退出。
- 收藏作品。
- AI 历史会话。
- 我的页面基础内容。
- RuoYi 内容管理的查看和编辑。
- 一条 XXL-JOB 排期同步任务。

### P1 后续补充功能

- RabbitMQ 异步统计。
- MinIO 反馈图片上传。

单人开发不要一次性制作完整运营后台。先确保作品、Banner、排期和 AI 反馈能够被自己维护，再增加复杂审核流程。

## 13. 阶段 G：质量、安全和运维

阶段预算：12 个工作日。

### 13.1 测试门禁

- 核心业务单元测试覆盖率目标不低于 70%。
- 登录、会话所有权、额度、幂等和删除必须有自动化测试。
- 首页、搜索、AI 主流程至少有一套端到端测试。
- 弱网、断网、重复点击、超时和重试必须手工验证。
- 每次发布都使用固定的 AI 评测集回归。

### 13.2 安全门禁

- 密钥、密码和访问凭证不进入源码、日志和提交记录。
- RuoYi 管理操作必须有角色限制和操作记录。
- 会话、收藏、文件和反馈必须验证所属用户。
- MinIO Bucket 默认私有，文件地址使用短期授权。
- 登录、AI、搜索和上传必须有频率限制。
- 生产和测试数据严格隔离。
- 用户删除和注销规则必须可以执行和验证。

### 13.3 备份和恢复

- PostgreSQL 每日备份。
- MinIO 业务文件和元数据按日备份。
- Redis 只保存可重建数据和短期状态，不作为唯一备份对象。
- 每月至少完成一次恢复演练。
- 首版目标：RPO 不超过 24 小时，RTO 不超过 4 小时。

### 13.4 运行指标

最低需要观察：

- 首页打开失败率。
- 搜索失败率和耗时。
- AI 首次内容出现耗时。
- AI 完整回答失败率。
- RabbitMQ 堆积数量。
- XXL-JOB 失败任务数量。
- PostgreSQL 连接和慢查询。
- Redis 内存和命中率。
- Elasticsearch 集群健康和查询失败率。
- 模型调用次数、成本和额度。

首版目标：

- 首页 P95 可交互时间不超过 2.5 秒。
- AI 首次内容出现 P75 不超过 3 秒。
- 核心功能可用性目标 99.5%。
- P0 故障必须可以在 4 小时内恢复或降级。

## 15. 阶段 I：发布和复盘

阶段预算：6 个工作日。

### 发布流程

1. 从 `dev` 合并到 `test`。
2. 完成测试环境验收。
3. 从 `test` 合并到 `release`。
4. 生成固定版本号和发布说明。
5. 备份数据并执行发布前检查。
6. 先小范围灰度，再扩大使用范围。
7. 观察错误率、AI 成本、队列和数据写入。
8. 记录发布结果和问题。

### 回滚条件

- 用户不能登录或核心页面无法使用。
- 用户会话出现越权或丢失。
- AI 出现大面积违规或严重剧透。
- 数据库迁移导致核心功能写入失败。
- 文件被未授权访问。
- 模型成本或请求量异常增长。

## 16. 单人开发的 CI/CD 规则

使用 GitHub Actions 或等价能力建立最小流水线：

```text
push feature/*
  -> 编译、单元测试、规范检查、依赖扫描
  -> 构建客户端和服务镜像

merge dev
  -> 自动部署开发环境

merge test
  -> 自动部署测试环境并运行回归

merge release
  -> 生成候选版本，等待手动发布
```

单人开发的合并检查清单：

- 是否只修改了当前任务范围。
- 是否处理成功、空数据、失败、重复和无权限状态。
- 是否增加或更新测试。
- 是否更新配置、迁移和版本记录。
- 是否检查日志中没有敏感内容。
- 是否知道如何回滚。

## 17. 风险和应对

| 风险 | 应对 |
| --- | --- |
| 一个人同时维护前后端导致进度慢 | 先做垂直链路，减少并行服务数量 |
| 微服务基础设施占用大量时间 | 组件按风险和必要性逐步接入，避免过度治理；单人开发保留明确边界 |
| AI 成本不可控 | 使用 Mock、每日额度、成本告警和固定评测集 |
| 数据源或图片授权不确定 | 第 1 周设置门禁，未确认时使用内部测试数据 |
| 长时间没有可见成果 | 每周必须产生可运行页面或可验证链路 |
| 发布后无法恢复 | 每月做恢复演练，发布前实际验证回滚 |
| 需求持续增加 | 新需求进入 P1/P2，不打断当前发布目标 |
| 个人开发中断 | README、部署脚本、决策记录和运行手册保持同步 |
