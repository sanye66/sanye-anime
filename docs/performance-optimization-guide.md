## 1. 目标与验收口径

性能优化必须同时守住四条边界：功能行为不变、错误与权限状态不退化、资源消耗有上限、收益可以复测。

| 层级 | 主要指标 | 本地门禁 | 生产建议 |
| --- | --- | --- | --- |
| 浏览器首屏 | 入口 JavaScript/CSS、LCP、CLS | `pnpm perf:check` | LCP ≤ 2.5 秒、CLS ≤ 0.1 |
| 页面交互 | 路由切换、长列表渲染、重复请求 | 类型检查、构建、页面回归 | INP ≤ 200 毫秒 |
| 服务接口 | p95、错误率、数据库查询数 | 单元测试、模块测试 | 核心读接口 p95 ≤ 200 毫秒、错误率 0% |
| 后台任务与导入 | 并发上限、超时、队列长度 | 受控线程池与超时测试 | 按来源限流，禁止无界并发 |
| 桌宠 | 隐藏窗口 CPU、入口资源 | 构建与可见性逻辑 | 后台不可见时不持续推进帧循环 |

前端告警阈值以[全系统监控方案](./monitoring-design.md)为准；历史接口 QPS 与压缩数据见[性能测试报告](./performance-test-report.md)。

## 3. 本轮实现说明

### 3.1 管理端按需加载

优化前，`main.ts` 全量安装 Element Plus，并由 Vite 固定生成约 919 kB 的框架块、104 kB 的图标块和389 kB 的全量样式。即使用户只打开登录页，浏览器也必须下载、解析和编译这部分代码。

本轮只注册实际使用的组件与对应样式，删除强制把整个包放进固定分块的配置。业务页面继续按路由拆分；用户把鼠标或键盘焦点移向导航项时，目标页面代码会提前获取。首次权限恢复把 `getInfo` 和 `getRouters` 并行执行，并使用单飞 Promise 合并重复导航触发。

收益来自三部分：减少网络字节、减少 JavaScript 解析/编译、把页面加载从“点击后开始”前移到“表达导航意图时开始”。

### 3.2 客户端渲染路径

客户端原有路由、HLS、ArtPlayer 和 Anime4K 已经动态加载，本轮保留这一边界。首页横幅增加高获取优先级和异步解码；卡片、搜索结果和相似作品使用 `content-visibility: auto`，浏览器可以跳过视口外元素的样式、布局和绘制，并通过固有占位尺寸保持滚动稳定。

该规则适合高度可估计的长列表，不应直接用于首屏标题、播放器或动态高度完全未知的区域，否则可能造成跳动。

### 3.3 服务端并发与查询

首页缓存未命中时需要“一个请求回源，其余请求等待同一结果”。旧实现把回源提交到 JVM 公共 `ForkJoinPool` 后，请求线程再同步等待，这会和其他公共池任务竞争，也会丢失请求线程上下文。本轮改为首个请求在线程内执行回源，其他请求只等待同一个 `CompletableFuture`。单飞语义不变，但资源边界更清晰。

目录列表仅在关键词搜索时才需要简介字段，因此空关键词列表不再读取简介映射。详情存储查询直接带 `status = '已发布'`，业务层不再先查卡片、再查状态、最后查详情。反馈状态更新后直接按主键回读，不再加载全部反馈后执行线性扫描。

### 3.4 桌宠后台节流

动画帧由递归定时器推进。窗口隐藏时继续运行不会产生可见价值，却会唤醒渲染进程。本轮在 `document.hidden` 时停止定时器，重新可见时继续，从而降低后台唤醒次数，同时不改变前台动画状态机。

### 3.5 安卓设备端桥接与本地库（VQ-60）

安卓页面不访问网关，它的“接口”是 Capacitor 桥接：`SanyeCatalog`（片库、历史、设置）、`SanyeSource`（公开来源搜索与预览）、`SanyePlayer`（横竖屏、全屏、常亮）。Capacitor 把全部插件方法投递到**同一条** `CapacitorPlugins` 线程执行，所以任何一次同步的 SQLite 或文件操作都会把后续所有桥接调用排在它后面。本轮据此做四件事。

其一，把升级挪到用户操作之前。数据库预热在插件装载时用一条 daemon 线程触发 `getWritableDatabase()`，建索引、加字段与封面回填都不再发生在用户第一次点开片库的那一刻；失败只记日志，由后续调用按错误码上报。

其二，把耗时查询变成索引查询。v7 增加 `saved_media_title (title)` 与 `watch_history_recent_full (updated_at DESC, media_url ASC, episode_id ASC, line_id ASC)`：前者让 v6 的封面回填不再逐行全扫片库，后者与 `listHistory()` 的排序完全一致，历史不再需要临时 B 树排序。v7 的标题索引在升级流程中先于 v6 回填创建，因此从 v5 直接升到 v7 也走索引。

其三，把线程池按职责拆开并让期限覆盖排队。搜索提交到独立的两线程池（竞速池扩到四线程以容纳两个并发搜索的两个入口），因此详情预览占满 6 条预览线程时搜索仍能立刻开始；`REQUEST_DEADLINE_NANOS` 改为在入队前起算，池满时的排队时间计入期限，界面不会再用「读取中」掩盖已经失败很久的来源。

其四，减少每次操作的固定成本。`recordProgress` 用 `INSERT OR REPLACE` 的返回行号判成败，去掉同一条记录的回读（播放中每 5 秒一次）；来源预览缓存超限时只淘汰最快过期的一条（原先满 24 条整表清空，浏览超过 24 部作品就把热点全丢掉）；首集探测改为保留已完成的结果，而不是第 0 条超时就丢弃全部。

收益的量级来自复杂度而不是常数：回填与排序从 `O(n × m)`／`O(n log n)` 临时排序降到索引访问，队列等待从「不计入期限」变为受 15 秒整体期限约束，读接口从「可能永久停在读取中」变为可重试的失败。

### 3.6 安卓播放体验与样式令牌（VQ-61）

播放体验这一轮的优化点全部落在「等待与失败要有出口」和「别做无谓的工作」两件事上，收益以可交互时间和内存峰值为口径。

其一，首帧之后的卡顿此前没有任何兜底。原来的 stall 看门狗四个分支都带 `hasFirstFrame` 直接返回，一旦出过画面再定格，只能等 hls.js 自己的 `fragLoadingTimeOut`（20 秒）乘重试次数才拿到致命错误，最坏接近一分半黑屏。现在 `waiting`/`stalled` 起一条 12 秒看门狗，每次 `timeupdate` 清表；超时即按线路失败处理，走既有的换线或随包线路接管，同时给出「网络较慢，正在缓冲…」。这条路径把「等待的尽头」从 hls 内部默认值收回到应用自己手里。

其二，缓冲区与清晰度按屏幕收敛。`maxBufferSize` 由 hls.js 默认的 60 MB 收到 40 MB（页面侧还有 64 MB 分片缓存，两者叠加时峰值内存偏高）；`capLevelToPlayerSize` 让自动档位不超过舞台实际像素，390px 宽的竖屏不会再拉 1080P 白耗流量与解码开销；`startLevel: -1` 让起播档位先取一个能立刻出画的低档。自动降档时给一次「网络较慢，已自动降到 XP」提示，避免用户把弱网降档当成画面故障。

其三，把不会用的数据先扔掉。片库/历史页的最大常驻内存来自分片缓存表（上限 64 MB）与原生缓存目录，此前两者都没有清理入口（`clearMediaCache` 在桥接里声明了却从未被调用）。现在「我的 → 存储 → 清理媒体缓存」同时清空内存分片表与原生缓存目录，弱网重看时的命中率会下降，但这也正是用户按下这颗按钮的预期。

其四，桥接调用补 JS 侧期限。原生已有 6 秒单请求／15 秒整体期限，但插件抛错或桥接丢消息时页面侧 Promise 会永久悬空（`previewPending` 里那条记录也就永远留在原地）。搜索与预览现在各加 15 秒客户端上限，超时按失败处理，在途记录随之出表。

其五，样式层的收益是「同样的视觉，更少的重复声明」。品牌色收敛为 `--brand-*`（38 处引用）、主题面与文字色走 `--app-*`（49 处引用），字号 64 处改走 8 个 `--font-*`、行高 7 处改走 `--leading-*`（替换逐项取原值，计算样式零变化）；量测口径（`android-style-metrics.cjs` + `count-hardcoded-colors.cjs`）下「未出现在任何令牌声明里的 hex」由 84 种降到 81 种，剩余 27 处一次性字号与 12 处一次性行高仍是字面量。另补一条 `prefers-reduced-motion: reduce` 的统一收口：此前整表只有按钮那一条规则，开启系统「减少动态效果」后控制条与货架的过渡照旧播放。主题令牌从 `.android-app` 提到 `:root` 并补 `prefers-color-scheme: light` 覆盖——后者同时修掉了挂载失败兜底页的实际缺陷：兜底页在应用根节点之外渲染，`var(--page-card)` 解析不到，实测卡面 `rgba(0, 0, 0, 0)`、边框 `0px`，修后实测卡面 `rgb(16, 37, 64)`、边框 `1px`、按钮底 `rgb(234, 242, 196)`。图标从自带字形的符号字符换成 13 枚线性 SVG，不再依赖系统字体与 emoji 字体的回退。竖屏重新露出「下一集／选集」后，全量审计抓到系统字体放大 ×2 时文字宽 66px 被 44px 固定方块裁掉（`overflow: hidden`），带文字的工具因此改为宽度跟内容走的 `--text`（仍以工具尺寸为下限），紧凑条也允许换行（加宽后 ×2 下最右「放大」实测 353..395，已超出 390px 视口；两行工具条优于裁字或横向溢出）；这也是一处只有压力场景（字体倍率）才会暴露的布局约束。

## 4. 性能优化教学

### 4.1 先建立基线，再选择手段

1. 明确用户动作，例如首次登录、打开详情、搜索、导入或播放。
2. 分解关键路径：下载 → 解析 → 渲染 → API → 数据库/外部服务。
3. 记录 p50、p95、错误率、请求数、查询数、入口字节和 CPU，而不是只看平均值。
4. 找到占比最大的步骤，只改变一个主要变量并复测。
5. 把收益变成门禁或监控，否则优化会随依赖和功能增长而消失。

### 4.2 估算模型

页面等待时间可以近似看成：

```text
页面时间 ≈ 网络往返 + 下载时间 + JS 解析/执行 + 渲染 + 最慢关键接口
```

串行接口的总时间接近各步骤相加，并行接口的时间接近最慢一步。并行不是越多越好：外部抓取并发必须小于来源、线程池和连接池能稳定承受的最小容量。

数据库查询应关注数量和扫描规模。按主键查询通常接近 `O(log n)` 或索引常数级访问；“读取全部再筛选”需要传输和构造 `n` 条记录，是 `O(n)`，数据越大差距越明显。

### 4.3 缓存与单飞的区别

缓存解决“重复计算”，单飞解决“同一时刻大量缓存未命中”。只有缓存没有单飞，缓存刚过期时仍可能出现几十次并发回源；只有单飞没有缓存，则每一批请求仍要回源。TTL 抖动用于避免大量 key 同时失效，空值短 TTL 用于阻止不存在数据反复穿透。

### 4.4 体积预算怎么定

预算应基于当前可接受基线并保留有限增长空间。本项目门禁统计 `index.html` 直接引用的 JavaScript 和 CSS gzip 总量，不把按功能动态加载的播放器、Anime4K 和桌宠精灵图错误计入入口包。媒体资源仍应通过图片格式、缓存头和授权来源单独治理。

当前预算：客户端 75 KiB、管理端 220 KiB、桌宠 70 KiB。若确有业务需要提高预算，必须在评审中附前后产物和用户收益，不能只修改阈值让 CI 通过。

## 6. 回滚与排障

| 现象 | 检查 | 回滚方向 |
| --- | --- | --- |
| 管理端组件无样式或不可用 | 检查组件注册和对应 `style/css` 导入 | 补齐单个组件；紧急情况下恢复全量注册 |
| 导航预取增加无效流量 | 核对触发范围和网络面板 | 移除对应悬停/聚焦预取，不影响路由懒加载 |
| 长列表滚动占位异常 | 检查 `contain-intrinsic-size` 与实际卡片高度 | 调整占位，或只移除该选择器的离屏规则 |
| 首页缓存请求等待异常 | 核对 in-flight Future 是否完成、异常是否传播 | 回退为同步回源并保留缓存，不恢复公共池阻塞模型 |
| 草稿详情意外公开 | 检查详情 SQL 的发布状态条件 | 阻断接口并恢复 `status = '已发布'` 条件 |
