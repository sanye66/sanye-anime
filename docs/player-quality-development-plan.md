## 1. 目标与当前基线

本计划在现有实时补帧与 Anime4K 增强管线之上，改善复杂运动画面、真实帧间隔、重增强预算、设备适配和可交付性。优化目标不是提高菜单标称值，而是在相同片源、设备、输出尺寸和测量方法下取得可复核的收益。

当前实现与已执行结果以[播放器开发设计](./media-player-development.md)和[播放器测试报告](./media-player-test-report.md)为准。2026-09-18 工作区已经具备双向稀疏光流、128/192/256/384 分析精度调整、原帧增强复用、GPU 完成计数、瓶颈分类和定时器节流回退。本计划不把这些已有能力重新列为待实现功能。

已有受控测试覆盖 1080p 高刷生成、遮挡、细线、切镜、短时启动和生命周期；其结果不能替代真实动漫整片观感、跨显卡兼容、物理高刷呈现或当前桌面安装物验收。第四步已完成 RIFE v4.6/ncnn Vulkan 的许可核对、本机隔离推理及同源光流比较，当时决定暂不进入 P4 常驻实时推理；权重仅在本地实验目录，常驻推理和实时端到端预算尚未验证，具体见[播放器测试报告](./media-player-test-report.md)。2026-09-21 按用户要求把同一候选接入为**预处理**引擎并随桌面包分发（见 P7，VQ-33～VQ-36），播放期实时补帧仍由现有光流承担，P4 的常驻实时推理结论不变，本轮代码未执行验证。

以下工作尚待开展：

| 优化方向 | 主要缺口 | 本阶段工程目标 |
| --- | --- | --- |
| 真实动漫画质 | 合成场景不足以覆盖形变、遮挡和压缩噪声 | 建立真实样本评估，减少已识别伪影 |
| 高画质与高帧率并行 | 重增强会触发回退，缺少分阶段预算对照 | 优化上传、缓存和处理顺序，量化可持续组合 |
| 神经网络补帧 | 原生模型尚未接入，端到端成本未知 | 先验证模型与传输预算，再决定实时接入 |
| 启动和设备适配 | 调度开销已有本机对照，刷新对齐后的长期功耗、设备差异与物理高刷仍未量化 | 限制调度开销，改善冷启动与设备配置恢复 |
| 真实显示能力 | GPU 完成帧不等于屏幕呈现帧 | 建立生成、合成器与物理显示分层证据 |

## 2. 执行原则与范围

1. 先建立可重复基线，再逐项修改；候选算法保持同源、同设备、同输出尺寸对比，不把降低原画尺寸当作同画质性能提升。
2. 复用现有 JSFeat、Anime4K、Worker 和 WebGL 管线。稠密光流、WebGPU 和原生推理仅在实验表明有收益后引入，不同时重写所有环节。
3. 每次绘制对应当前有效媒体时刻；禁止重复原帧、批量重放过期帧或以计划时间替代真实测量来满足帧率门禁。
4. 浏览器保留现有回退路径。原生推理候选只在桌面端评估，网页端不依赖本机额外安装的服务。
5. 超分输出不等于原生高分辨率素材；片源码率、解码、显示器刷新率和驱动仍是能力边界，不承诺 UHD 770 上最高超分与 240 FPS 同时成立。
6. 本文不修改已有菜单与默认产品行为。后续确需新增模式或改变默认策略时，先同步 `product/` 唯一事实源，再实施对应技术变更。

2026-09-18 按用户要求依次执行 P0（VQ-01～VQ-03）、P1（VQ-04～VQ-06）、第三步 P2（VQ-07～VQ-09）和第四步 P3（VQ-10～VQ-12）。正式任务及状态登记在[开发任务清单](./development-tasks.md)，本文保留拆分和依赖，执行证据集中进入[播放器测试报告](./media-player-test-report.md)。P3 以“本机候选暂不采用”收口，不表示实时门禁通过；P4 保持条件未满足，P5 仍为后续工作包。

## 3. 阶段安排

建议单人按下表顺序执行。工期为具备素材、设备与工具链后的有效工程人日，不是交付日期；外部设备、模型下载与许可核对等待不计入。阶段出口不满足时先修正或缩小候选范围，不直接开启默认使用。

| 阶段 | 内容 | 前置依赖 | 估算人日 | 阶段出口 |
| --- | --- | --- | --- | --- |
| P0 | 测量、样本和证据基线 | 当前代码与本机环境 | 3–5 | 可重放的对照样本与性能预算 |
| P1 | 调度开销、启动与设备适配 | P0 | 4–6 | CPU 开销与高刷稳定性同时可控 |
| P2 | 复杂运动画质和 GPU 管线 | P0，调度结论使用 P1 基线 | 6–10 | 伪影改善与处理成本对照通过 |
| P3 | RIFE 等候选可行性实验 | P0、P2 数据 | 3–5 | 明确采用、受限采用或暂不采用 |
| P4 | 常驻原生推理集成 | 仅 P3 通过后执行 | 8–15 | 寻址、取消、故障回退与包内运行通过 |
| P5 | 高刷显示、整片与桌面验收 | P1、P2；采用模型时还需 P4 | 4–7 | 对目标设备给出支持矩阵和交付证据 |
| P6 | 起播画质、增强稳定性与预算重分配 | P0、P1；起播测量入口 | 9–15 | 起播清晰度与补间/增强就绪达标，档位不再单向丢失 |

不含原生模型集成的路径约 20–33 人日；P4 被采用时总计约 28–48 人日。P3 可得出暂不接入的有效结论；这不阻断现有管线的独立改进和验收。

### P3：神经补帧可行性

| 编号 | 工作与交付物 | 验收条件 |
| --- | --- | --- |
| VQ-10 | 固定 RIFE/ncnn 等候选的代码提交、模型版本、权重摘要、代码及权重许可、所需 GPU 特性 | 明确可分发范围和包体积；代码 MIT 不能代替权重许可核对；不满足条件的候选标记阻塞原因 |
| VQ-11 | 先用合法帧对执行本机推理实验，再测连续帧、任意时间步和传输开销；对照现有光流 | 输出质量、预热、P50/P95 耗时、内存/显存、输入输出拷贝均有证据；不能把文件处理速度直接当作实时播放速度 |
| VQ-12 | 编写技术决策，确定适用设备、源帧率、输出尺寸、目标帧率与回退路径 | 质量确有改善且端到端预算有余量才进入 P4；否则保留现有路径，并给出被拒绝候选的实测原因 |

对 24 FPS 至 120 FPS 的实验，每个原帧间隔通常需要生成四个中间时刻；必须按全部推理、上传、合成与同步成本计算可持续吞吐，不能用一次中点推理耗时代表整个间隔。源帧率变化、重复帧和可变帧率视频按实际时间戳调度，不固定按整数倍假设处理。

#### 6.2.1 VQ-25 起播清晰度记忆（2026-09-20 已实施）

实现位置为 `sanye_client/src/video/playbackPreferences.ts`（记忆存取与档位匹配）与 `sanye_client/src/views/animeDetailView.vue`（起播定档、回落与写回）。

- 记忆内容：按播放地址保存档位阶梯签名、档位序号、高度、码率、来源（自动或手动）与写入时间；同地址每个来源只保留最新一条，总上限 50 条。
- 有效期：自动记录 7 天，手动选择 30 天；过期、未来时间戳或字段非法的条目按无记忆处理，用户清除浏览器存储后自然回到低档起步。
- 起播：`hls.js` 关闭自动开始加载，清单解析后把记忆档位匹配到当前阶梯（阶梯一致沿用原序号，否则按同高度与最近码率匹配），命中高于低档且不超出窗口降档上限时先设 `startLevel` 再显式 `startLoad()`，随后仍由带宽自适应接管；匹配不到、结果为低档或被窗口上限压到低档时保持原低档起步。
- 回落：记忆档位在 2000ms 内没有出画即作废该记录，`stopLoad()` 后按低档重新起播，避免首帧继续等待高码率分片；记忆档位出现致命 `hls.js` 错误同样作废。回落为内部行为，本轮不新增提示文案。
- 写回：播放 1 秒后开始记录，只有正在播放的实际档位发生变化时才更新自动记录；手动选择档位立即写入手动强偏好，切回「自动」只清手动记录。

| --- | --- | --- | --- | --- |
| 冷启动（无记忆） | 169.8–196.1 | 293.6–350.5 | 640 | 2291.6–2388.0 |
| 同地址再次起播（有记忆） | 100.9–190.5 | 137.2–244.7 | 1280 | 137.2–244.7 |

#### 6.2.2 VQ-26 增强档位有界恢复（2026-09-20 已实施）

旧口径在 `receiveFrame` 内用 `slowEnhancement` 累计“连续 3 个慢帧”（30 FPS 下约 100ms）即调用 `downgradeEnhancement`，此后实际档位永久停在较低一档。受控夹具已复现代价：640×360 的 2× 超分在无头软件渲染下约 1 秒降到性能档，之后 30 秒不再回到请求档位。

新判定移到 `enhancementBudgetPolicy.ts`，由渲染 Worker 每帧提交样本并返回 `hold` / `downgrade` / `recover`：

- **持续压力按墙钟时长判定**：压力段从第一个超预算样本开始累计（增强耗时超过单帧预算 62%，或增强队列积压 ≥ 6），必须同时覆盖 800ms 且包含至少 3 个样本才降档；连续两个有余量样本才结束压力段。实测过载管线会把自身采样节流到每秒 5–11 个样本，因此口径不能依赖固定样本窗比例；而健康管线里的 3 帧尖峰在几十毫秒后就被有余量样本结束，达不到时长门槛。
- **恢复有冷却与稳定门槛**：降档后先冷却 5 秒，再累计 3 秒且不少于 20 个有余量样本（耗时不超过预算 45%、队列 ≤ 1）才升一档；每次只升一档，且不超过可恢复上限。
- **可恢复上限**：默认等于会话起点档位，因此 240 FPS 极致帧率的画质平衡不会被恢复抵消；超分纹理预算与增强初始化失败属于结构性限制，会把上限锁定到实际档位；换源或换分辨率时按会话上限重新评估，再次越界会在下一次降档重新锁定。
- **有界恢复**：升档后 20 秒内再次降档记为一次恢复失败，冷却按次翻倍（5→10→20→40→60 秒上限），恢复过程不出现档位往返振荡。
- **档位与记录**：请求档位、实际档位、可恢复上限、本窗口档位变化类型与每次变化的档位/原因/时刻都进入统计；恢复到请求档位时清空回退原因，仍低于请求档位时保留原因。恢复本身不新增用户可见提示文案，档位与清晰度的统一说明由 VQ-30 提供（见 6.2.6）。

受控证据（`e2e/enhancement-recovery.test.cjs`；Windows 本机、Playwright 1.62.1 无头 Chromium 软件渲染、Vite 开发服务、640×360 源帧 + 2× 超分、34 秒窗口）：新入口先在没有 GPU 的环境里直接驱动判定类，覆盖瞬时尖峰、亚秒抖动、四分之一超预算、增强查询周期性排空、冷却窗口、稳定样本门槛、恢复失败退避与不可恢复上限；再在真实渲染 Worker 中观测到 upscale→restore（2.86 秒）、restore→fast（3.74 秒）、fast→restore（11.82 秒，距上次变化 8.08 秒）、restore→fast（13.01 秒，恢复失败 → 冷却 10 秒）、fast→restore（26.03 秒，距上次变化 13.02 秒）与随后降档。每次变化只升降一档，实际档位从未高于请求档位与可恢复上限，重档位的回退记录与恢复记录都写入统计。

命令与逐窗口数据见[播放器测试报告](./media-player-test-report.md)。边界：该夹具分辨率下重档位持续超出增强预算，因此“恢复后又被降档”是本环境的预期结果，用于验证退避有界；真实显卡若可持续承载请求档位，不会出现恢复尝试。真实动漫片源、跨设备与桌面安装物仍待环境。

#### 6.2.3 VQ-27 源帧率达标时跳过光流补帧（2026-09-20 已实施）

补帧只在源帧率低于目标帧率时产生新画面。旧实现无条件执行“缩放源帧 → 投递光流分析 → 上传前向/反向运动场”，60 FPS 源在 60 FPS 目标下仍然付出这套成本，而每个展示时隙本来就能拿到一张原帧。新判定与执行位置：

- **判定模块**：`sanye_client/src/video/interpolationDemandPolicy.ts`。源帧率取最近 16 个样本的中位数，`≥ 目标 × 0.92` 记为“无需补帧”，`≤ 目标 × 0.8` 才回到补帧；中间为滞回带。进入需覆盖 400ms 且不少于 6 个连续样本，退出需覆盖 700ms 且不少于 8 个连续样本；目标帧率变化（自适应升档或用户改档）只清空连续证据并保留当前模式。
- **源帧率来源**：主线程按媒体时间测量相邻画面间隔（`requestVideoFrameCallback` 的 `metadata.mediaTime` 差值）并随帧上报，取中位数估计。这样偶发呈现丢失、合成器少一次回调只改变少数样本，不会把 60 FPS 源估成 50 多；而真实换档（例如 60→24）会在一到两个窗口内被识别。本线程因繁忙丢弃帧不再影响该估计。
- **执行旁路**：命中“无需补帧”时不再创建缩放位图、不再投递光流工作线程、不上传运动场纹理，只上传原帧并进入帧队列；绘制阶段把相位吸附到最近原帧，着色器在相位 0/1 直接输出该原帧并保留既有锐化与增强。增强档位、输出尺寸与展示时钟不受影响，画布保持可见。
- **统计**：新增 `interpolationNeed`（`flow` / `none`）、`interpolationReason`、`flowSkippedFrames`（窗口内跳过的光流分析次数）、`flowSkippedTotal` 与 `interpolationDemand`（源帧率估计、目标比例、样本数、模式变化次数、原因）。`interpolationDemand: 'always'` 作为隔离对照开关保留，用于与优化前路径做同源比较，默认 `auto`。

受控证据（`e2e/interpolation-bypass.test.cjs`；Windows 本机、Playwright 1.62.1 无头 Chromium、Vite 开发服务 `localhost:5173`）：

- **真实播放链路**：640×360、60 FPS、24 秒本地 HLS 夹具，以「补帧目标 60 + 画质 fast」经外部预览播放器播放，判定完成后窗口源帧率估计为 60、`interpolationNeed` 为 `none`、每窗跳过 45–49 次光流分析且分析次数为 0、合成帧为 0、呈现时隙 49–52、停顿帧为 0，增强画布保持可见。
- **同源对照**：同一 320×180 夹具分别用 `auto` 与 `always` 运行。`auto` 的 60 FPS 段每窗分析次数为 0、`computeMs` 为 0，纹理上传中位数为 1.0/帧；`always` 每窗分析次数与上传帧数一致，纹理上传中位数为 3.05/帧（原帧 + 前向/反向运动场），差别即被消除的光流成本。
- **滞回与恢复**：源降到 24 FPS 后窗口内恢复补帧（分析 14–26 次/窗、补间帧 29–59/窗），源帧率回到 60 后重新进入旁路；一次会话内模式变化不超过 3 次，未出现开关式抖动。判定语义另有单元级用例覆盖滞回带、目标改档、偶发丢帧与时间轴重置。
- **像素对照**：旁路帧窗口内输出最近原帧（中心像素与源帧逐字节相同），对照在窗口中点输出两帧之间的合成色；相位 0 与 1 上旁路与光流路径的输出逐字节一致，说明差异只来自“是否生成新画面”，不是增强或锐化差异。

边界：60→60 时对照本身也会产生少量合成帧，因此两种模式的差异是“最近原帧”取代“同源帧间运动补偿混合”，差值在 1/60 秒量级；没有真值样本，不宣称 PSNR/SSIM。本机受控夹具为合成帧与本地 HLS，真实动漫片源、跨显卡、桌面安装物与物理刷新呈现仍待环境；本机 1080p 高刷门禁（`realtime-interpolation` 的 live 项与 `player-quality` 的高刷矩阵）在当前负载下未通过，前者已做改动前后对照且两版都失败，见播放器测试报告。

#### 6.2.4 VQ-28 仅增强路径移入渲染 Worker（2026-09-20 已实施）

「只开画质、不开补帧」原先在页面主线程逐帧执行 `anime4k.js` 的 `VideoUpscaler`；受控窗口记录到 3 秒内 44 次主线程长任务（最长 78ms），页面主线程帧间隔中位数 66.7ms。补帧开启时增强本来就在渲染 Worker 内执行，同一窗口没有长任务。VQ-28 把仅增强路径也放进同一个 Worker，并且**只改变执行位置、不改变像素输出**：

- **同一条档位链路**：新增 `profileShaderChain(profile)` 作为档位链路的唯一定义（性能 = `Deblur_DoG`；均衡/修复 = `Clamp_Highlights` + `Restore_CNN_S`；锐化 = `Clamp_Highlights` + `Restore_CNN_M`；超分 = 追加 `Upscale_CNN_x2_S`）。主线程 `anime4kRuntime.createAnime4KVideoUpscaler` 与渲染 Worker 的仅增强路径都调用它，避免两份配置漂移；`FrameEnhancer` 的放大倍率改为读链路自身的 `magnification()`，不再按档位名硬编码 2×。
- **执行模式**：Worker 初始化新增 `interpolation: false`。该模式不创建运动估计线程、不引入插值延迟、不建立音频路由，并通过判定模块的 `forceBypass` 固定在“不执行补帧”；仅增强路径同时关闭 Worker 内的自动降档与恢复，避免用静默降档替换用户选择的档位。
- **呈现**：新增仅增强专用绘制路径，只把「包含目标媒体时刻的最近原帧」画上去。延迟为 0 时目标时刻经常越过最新原帧，那属于正常推进，因此不计 `missedPairs` / `stallFrames`；同一张增强纹理只在对应原帧首次轮到呈现时提交一次。统计新增 `enhancementOnly`。
- **回退**：Worker 初始化握手（`ready`）失败（模块不可用、档位链路初始化失败、5 秒内无响应）时回退原 `anime4k.js` 主线程路径；`playbackPreferences.enhancementPath` 提供 `worker`（默认）与 `main` 一键切换，只用于隔离对照与回退，不进入播放器菜单，也不新增提示文案。

受控证据（`e2e/enhancement-thread-migration.test.cjs`；Windows 本机、Playwright 1.62.1 无头 Chromium、Vite 开发服务 `5173`）：

- **像素对照**：同一张 320×180 受控源帧分别交给 anime4k.js 的单帧管线（与主线程 `VideoUpscaler` 同一套着色器与 hook 顺序）和渲染 Worker 的同一渲染器。五个档位的 RGB 通道逐字节一致（性能/均衡/锐化/修复各 172,800 个通道、超分 691,200 个通道，最大偏差 0、不同通道 0），输出尺寸也一致（超分 640×360，其余 320×180）。唯一差异在性能档的 alpha 通道（4,196 个像素、最大 25/255）：`Deblur_DoG` 本身不写 alpha，两条路径的最终装配方式不同；播放画面是不透明的视频帧，该项单独记录、不计入画质结论。
- **主线程占用**：640×360、30 FPS 本地 HLS 夹具、4 秒稳定窗口。原主线程路径（`enhancementPath: 'main'` + 锐化）为 61 次长任务（最长 65ms）、页面主线程帧间隔中位数 66.7ms；渲染 Worker 的锐化与性能档均为 0 次长任务、帧间隔中位数 33.3ms，增强画布保持可见，输出 640×360，`interpolationNeed` 为 `none`、合成帧 0、每窗跳过 15–30 次光流分析、停顿帧 0。
- **判定与回退**：`forceBypass` 在 24/30/55/60/120 FPS 共 630 个样本上始终返回不补帧且无模式变化；把渲染 Worker 模块请求置为失败后，页面回退到主线程 `anime4k.js` 路径（`.sanye-anime4k-active`），无未捕获错误且播放不中断。

回归：`progress-seek-latency` 四类配置通过，其中仅增强配置由迁移前的 44 次长任务（最长 78ms）变为 0 次；`interpolation-bypass` 7 项、`enhancement-recovery` 6 项、`quality-fluctuation` 与 `frame-menu-state` 等 11 项、`playback-pipeline` 8 项、`startup-quality-timeline` 3 项、`playback-experience` 2 项、`player-quality` 4 项（含 1080p 高刷矩阵）、`realtime-interpolation` 4 项、`worker-generations` 5 项与 `enhancement-models` 1 项全部通过；`pnpm typecheck` 通过。边界：页面无法驱动渲染 Worker 持有的 OffscreenCanvas WebGL 上下文，Worker 运行期上下文丢失路径未单独触发，主线程路径的上下文丢失用例固定 `enhancementPath: 'main'` 保留；真实显卡、真实动漫片源、跨设备与桌面安装物仍待环境。

#### 6.2.5 VQ-29 补帧延迟自适应收缩（2026-09-21 已实施）

旧口径把补帧路径的视频与音频都固定在 150ms：`target` 必须落后最新源帧 `delay`，因此起播与定位恢复都要等窗口填满 150ms 才出补间层，这段原画窗口在受控夹具里对应「首帧 → 补间层就绪」约 0.19–0.35 秒。VQ-29 把延迟改成按实测需要收缩的预算：

- **判定模块**：`sanye_client/src/video/interpolationDelayPolicy.ts`。下限取 `max(2 个源帧间隔, 40ms)`、上限仍是页面传入的 150ms；每个播放段（起播、定位、暂停恢复、缓冲、换源与时间轴跳变）从上次证明可用的延迟起步，`playbackPreferences.interpolationDelay`（`adaptive` 默认 / `fixed`）只用于隔离对照与回退。
- **未接管呈现前加宽**：窗口覆盖不到目标时刻时，按「最新源帧老化时间 + 1.5 个源帧间隔」直接加宽（单次至少 +10ms，封顶 150ms）。此时画布尚未生效，加宽不会被观察到画面回跳。
- **收缩需要连续余量**：连续两个干净窗口（无未命中配对、无停顿、无回跳）、窗口内最坏实测需要仍留出 ≥ 15ms 余量、且距上次变化 ≥ 1 秒时才收缩一步（20ms），并且不低于下限。收缩只让画面向前推进。
- **停顿期间恢复余量**：目标时刻越过最新源帧并持续 100ms 以上时，画面正在重复同一帧；这段停顿内按实测需要恢复一步（40ms，受 1 秒冷却与上限约束）。播放段起点同样按登记的压力恢复一步。正常推进时不做加宽，因此不会把已经播过的画面重新显示。
- **音画同步**：页面把同一延迟写回 Web Audio 延迟节点，起播与定位按目标值直接写入，播放期变化用 40ms 斜坡跟随，音频延迟与生效视频延迟的偏差不超过一个收缩步长。
- **不影响既有结论**：仅增强路径（VQ-28）不引入插值延迟，不受本项影响；超分纹理预算（VQ-26）改按会话上限而不是当前生效延迟计算，避免收缩放宽既有可恢复上限。

受控证据（`e2e/interpolation-delay-adaptive.test.cjs`；Windows 本机、Playwright 1.62.1 无头 Chromium、Vite 开发服务 `5173`、640×360 30 FPS 12 秒本地 HLS 夹具带音频、补帧目标 60、画质关闭）：

- **判定语义**（无 GPU 也能执行）：起播从最小可用窗口起步、加宽单调不减且封顶 150ms；播放段首个窗口是预热窗口、不据此登记压力；停顿与未命中配对窗口只登记恢复且每次只走一步；连续干净窗口逐级收缩到下限；播放段内恢复与起点恢复分开计数。
- **真实播放链路**（专项入口，每种口径三轮取中位数，三次连续运行）：首帧 → 补间层就绪时长固定 192.9 / 211.7 / 196.6ms → 自适应 114.4 / 119.5 / 116.9ms；定位后原画窗口（每轮三次拖动取中位数）固定 262.0 / 267.6 / 257.4ms → 自适应 176.1 / 181.3 / 175.1ms；`ready-data` → `interpolation-active` 标记窗口固定 339.8 / 333.8 / 344.8ms → 自适应 253.4 / 266.5 / 249.3ms。同一入口 `startup-quality-timeline`（自适应默认，三次连续运行，非同次运行对照）的补间层就绪窗口为 0.23–0.29 / 0.23–0.30 / 0.26–0.28 秒，低于同口径文档基线的 0.69 / 0.32 / 0.38 秒。
- **门禁**：起播生效延迟 66.7ms（= 2 个源帧间隔）且不高于会话上限 150ms；音频延迟跟随为 66.7ms，稳定段与定位后的音画绝对偏差都是 0ms（门禁 ≤ 40ms）；正常推进的画面回跳为 0；恢复余量只出现在已经停顿或未命中配对的窗口、每次只走一步且次数不超过恢复次数；输出 640×360、生效档位与固定延迟一致，合成帧仍正常产出；`interpolation-delay-adaptive`、`quality-fluctuation`、`interpolation-bypass`、`progress-seek-latency`、`realtime-interpolation`、`startup-quality-timeline` 与 `enhancement-recovery` 共 28 项与 `pnpm typecheck` 全部通过。帧队列保留深度按会话上限而不是当前生效延迟计算，收缩只改变展示时刻、不减少可回退缓冲，VQ-24 的整层稳定与 VQ-27 的停顿门禁因此保持通过。

#### 6.2.6 VQ-30 画质可观测性（2026-09-21 已实施）

实施前 `AdaptationNotice` 只能解释帧率降档与增强档位回退，播放器既不记录“当前清晰度是不是最高档”，也没有地方回答“为什么不是最高清”：VQ-25 的记忆回落、VQ-26 的恢复与 VQ-27 的旁路都只写进统计字段。VQ-30 把这些事实按同一个时间窗口汇总，并给出可自证原因的界面说明。

- **汇总模块**：`sanye_client/src/video/qualityObservability.ts`。页面每秒采样一次 HLS 清晰度状态（`currentLevel`/`loadLevel` 的高度与码率、阶梯最高档、比当前高一档的档位及按 `abrBandWidthUpFactor` 换算的升档需求、`autoLevelCapping` 对应的窗口尺寸上限、`manualLevel` 表示的手动来源、`bandwidthEstimate` 与 VQ-25 记忆回落说明）；渲染 Worker 的统计窗口把 `stallFrames`、`analysisWidth`、`effectiveProfile`/`requestedProfile` 与 `qualityFallbacks` 合并进同一窗口，页面另外累计媒体 `waiting` 次数。
- **原因归纳**：按「用户手动选择 → 起播记忆回落 → 播放窗口尺寸上限 → 带宽不足（估算带宽低于升档需求）→ 播放中停顿 → 带宽自适应」取第一个能被同窗口数据证实的原因，说明固定写成「当前 XP（最高 YP）：原因」。
- **瞬时提示**：只在自动档位从已知档位变化到更低档时提示一次（`清晰度已调整：…`）；同一高度在回到最高档前不重复播报，相邻两次提示保留 5 秒最小间隔；被最小间隔拦下的降档登记为待播说明，档位不再变化时在下一个窗口补齐，避免真实降档被静默吞掉。起播低档起步（`startLevel: 0`）与手动选择都不算档位变化，分别由既有起播行为与清晰度菜单的切换提示说明。
- **可查询说明**：清晰度菜单新增「当前清晰度说明」项，读取同一份窗口汇总（含画质回退、落后帧与运动分析宽度）；该项不改变档位与控件标签，回到最高档时说明改为「当前已是最高清晰度 XP」。两条路径都不新增常驻面板。
- **诊断通道**：最近 30 个窗口挂在播放器实例的 `sanyeQualityWindows` 上，只服务自证与自动化读取，不进入界面，也不改变 `hls` 档位、增强档位、延迟预算与菜单选项。

受控证据（`e2e/quality-observability.test.cjs`；Windows 本机、Playwright 1.62.1 无头 Chromium、Vite 开发服务 `5173` 与生产构建预览 `4173`、本地双档 HLS 640×360 与 1280×720）：

- **窗口汇总与原因语义**（无 GPU 也可执行）：三档阶梯上验证窗口同时带上生效档位、阶梯最高档、带宽估计、`stallFrames`、`analysisWidth`、媒体等待与 `qualityFallbacks`；原因优先级覆盖手动、记忆回落、窗口尺寸上限、带宽不足、播放停顿与自适应；清单解析前的未知档位不写入窗口，窗口历史以 30 条为上限。
- **提示语义**：首个可比较窗口、同一档位的连续窗口与手动选择都不提示；自动降档提示带当前档位、最高档与原因；同一高度不重复播报，回到最高档后可以再次提示；最小间隔内的降档在下一个窗口补齐。
- **真实播放链路**：大窗口下带宽自适应先升到 720P（首窗 1280），给高档分片加 3 秒延迟后回落到 360P；窗口 `当前 360P（最高 720P）：带宽自适应：估算 3.2Mb/s`，同窗口带宽估计 3.23Mb/s（升档需求 3.06Mb/s）、落后帧 21–25、运动分析宽度 128、回退历史为空数组；界面提示与窗口汇总逐字一致，可查询说明等于最新窗口摘要；清晰度菜单仍保留「自动 / 720P / 360P」，说明项不替换控件标签。
- **回归**：`quality-fluctuation`、`startup-quality-timeline`（2 项）、`progress-seek-latency`（四配置）、`interpolation-delay-adaptive`（5 项）、`interpolation-bypass`（9 项）、`enhancement-recovery`（6 项）、`realtime-interpolation`（4 项）、`playback-pipeline`（3 项）、`playback-experience`（2 项）、`frame-menu-state` 与清晰度专项 `e2e/e2e-media-quality.mjs`（4/4）通过，`pnpm typecheck` 与 `pnpm --filter @sanye/sanye_client build` 通过。

边界：档位窗口与提示来自无头浏览器与本地夹具，判据是「说明与同窗口数据一致」，不宣称真实网络的降档预测准确率；本机 1080p 高刷门禁与 `progress-seek-latency` 在负载窗口内首次运行未通过、去掉并发负载后复跑通过，保留为环境相关失败；真实显卡、真实动漫片源、跨设备与桌面安装物仍待环境。

#### 6.2.7 VQ-31 高刷与物理呈现（2026-09-21 已实施）

实施前，播放器只把「GPU 完成确认的生成帧」当作输出结论：统计里的 `outputFps` 来自渲染 Worker 的 GPU 完成查询，页面只额外记录主线程动画帧数，无法回答「生成了多少帧里有多少真的被看到」。目标高于刷新能力时，提交由脚本计时器在截止时刻唤醒，计时器迟到就跳过期时隙：本机 60Hz、1080p、30 FPS 源 → 120 目标、锐化档下，末两窗生成帧率降到 89–96/秒并把目标档降到 60，提交相对理想时刻迟到 P95 约 15ms；被呈现的那一帧相对刷新边界的陈旧度 P95 为 17.3–18.2ms，已接近一个刷新周期（16.7ms）。

VQ-31 做两件事：把四层分开记，再把提交放到刷新边界上。

- **分层计量**：新增 `sanye_client/src/video/presentationLayers.ts`。每个一秒窗口分别记录源帧（媒体元素 `presentedFrames` 增量）、生成帧（GPU 完成计数，含补间帧）、合成器提交（渲染 Worker 每次实际提交绘制）与可观察呈现（画布作为可见层时的主线程动画帧数）；另记刷新边界上被呈现帧的内容陈旧度 P95。判读分四类：`aligned`（目标不高于刷新能力，提交落在刷新时隙）、`refresh-bound`（目标高于刷新能力，生成帧率可达成而可观察呈现只能到刷新上限）、`deadline-paced`（刷新未知但仍有呈现样本）与 `unconfirmed`（没有呈现样本）。窗口固定带 `physical: 'unverified'`：浏览器内没有扫描提交证据，验收不得把可观察呈现写成物理呈现已确认。
- **呈现对齐**：`PresentationScheduler` 新增 `PresentationAlignment`，默认 `refresh`。目标高于刷新能力时不再只按理想截止时刻唤醒，而是在刷新边界回调里提交，并把边界前已到期的时隙按各自理想时刻补齐（一个边界内最多 4 个时隙，覆盖 60Hz 屏幕上的全部目标档位）；超过上界仍按跳过处理，继续交给既有帧率稳定逻辑降档。边界回调没有实际到达（例如标签页隐藏或线程被长任务占用）时由交付确认退回截止时刻计时器，并保留只读刷新边界探针用于呈现统计。`presentationAlignment: 'deadline'` 保留优化前的计时器节拍作为隔离对照，不出现在播放器菜单里。

#### 6.2.8 VQ-32 稳定优先简化（2026-09-21 已实施）

用户反馈「画面波动很大」，并要求降低复杂设计、以帧率为主、画质为辅、稳定与丝滑。按本轮改动前的实现，播放期内有三处会**反复改变画面**的自适应，彼此还会互相触发：

1. 帧率目标在连续 20 个稳定窗口后回升一档（`frameCadence.ts`），一旦再次超预算又降回去；本机受控窗口里 120 目标在 144/165 目标下都出现过这种往返。
2. 增强档位在持续有余量后升回请求档位（VQ-26 的有界恢复），受控夹具里观测到 8–13 秒一次的 upscale→restore→fast 往返；每次升档都会改变画面清晰度。
3. 补帧延迟在连续干净窗口且余量 ≥ 15ms 时收缩 20ms（VQ-29），收缩后在真实抖动下又按步恢复余量（画面回跳）。受控夹具里这段表现为「顺畅一小段 → 停顿重复帧 → 回跳」。

本轮把这些自适应在播放期内收敛为**单向**，只保留真正需要的方向：

- **帧率目标只降不升**：删除稳定回升分支；自动档在未因压力降档时跟随刷新能力（在 144/165Hz 能力上直接对齐能力上限，不再需要 20 秒才升档），一旦降档就保持到下一个播放段。内部重建（例如画质档位降档触发的 `reset`）不再把目标帧率顶回请求值，避免「降画质 → 帧率回档 → 再超载」的循环；起播、定位、换源与尺寸变化仍是新播放段，按请求档位与刷新能力重新定档。降档仍只由渲染/呈现持续不足触发，增强与运动分析压力继续由画质让路处理。
- **增强档位只降不升**：删除恢复动作、冷却、失败退避与可恢复上限（`enhancementBudgetPolicy.ts` 只输出 `hold` / `downgrade`）。降档判据不变（墙钟 800ms 且至少 3 个样本的持续预算压力）；需要更高档位时由用户在画质菜单里重新选择，那会重建会话并重新评估预算。
- **补帧延迟只加宽不收缩**：`observeWindow` 不再收缩，只登记压力与说明；未接管呈现前的按需加宽与「目标越过最新源帧、画面正在重复同一帧」时的余量恢复保留，因此停顿仍能被纠正，正常推进的画面回跳仍为 0。

不改变的部分：输出尺寸、画质档位链路与像素输出、清晰度（HLS 档位）决策、展示时钟与刷新对齐、音画同步模型的其余部分、`qualityFallbacks` / `qualityChange` / `interpolationDelay` 统计字段（只去掉已删除动作对应的字段）。

## 5. 测量口径与建议门禁

### P19：切档丝滑、降级可见、定位跟手（VQ-59，2026-09-30）

**用户反馈**：「在切换挡位或者降级时画面与声音出现明显的波动，而且降级之后在列表上并没有体现出来，要求画质与帧率切换要丝滑，而且在高画质帧率情况下，拖动进度条的速度过慢，进行优化」。

**根因（三条各自独立）**：

1. **切档/降级波动**：会话没有「原地换档」的 API，`startRealtimeInterpolation` 只返回 `{canvas, stop, deferJudgement}`，所以页面每次切档都走 `stopEnhancement()` 再重建：画布被移除又插回，音频延迟被 `setDelay(0)` 清零再抬回——用户就是画面闪一下、声音抖一下。
2. **降级未体现**：画质/帧率列表只按**用户请求**标 `aria-pressed`，没有任何位置显示**实际生效**的档位，所以 240 极致帧率把画质平衡到性能档之后，列表里看不出发生过降级。

### P17：画质增强的 WebGPU 化（VQ-57，进行中，2026-09-30）

**目标**：把 Anime4K 从 WebGL1 搬到 WebGPU。动因是 WebGL1 版依赖 `WEBGL_color_buffer_float` 才能用 32 位浮点中间纹理，缺这个扩展的机型只能退回「性能」档（只有 Deblur_DoG），画质反而更差。

**本轮完成**：

| 编号 | 工作与主要位置 | 证据 |
| --- | --- | --- |
| VQ-57a | 机械转译器 `sanye_client/scripts/generate-anime4k-wgsl.mjs`：把 anime4k.js 里机器生成的卷积段（`go_N` 采样宏、`mat4` 权重字面量累加、残差项）转成 WGSL，并在生成期拒绝残留 GLSL 语法或未转译标识符 | 生成 `src/video/anime4kWgsl.generated.ts`，8 趟（`restoreS` 4 + `upscaleS` 4） |
| VQ-57b | 手写规则外的两段 `src/video/anime4kWgslManual.ts`：`Clamp_Highlights` 三趟（循环取邻域亮度极值 + 跨趟 STATSMAX）与 `Upscale_CNN_x2_S` 收尾趟（按子像素序号挑通道，WGSL 不允许动态下标 vec4） | 与生成段落共用 48 字节 uniform 布局 |
| VQ-57c | 档位链路 `src/video/anime4kWebgpuPlan.ts`：均衡/修复 = clamp 三趟 + Restore_CNN_S 四趟 + PREKERNEL 阶段收尾 clamp 三趟；超分 = 再加 Upscale_CNN_x2_S 五趟并在 2× 上收尾 clamp | 函数级可复核，`null` 即明确回退 |
| VQ-57d | 运行时 `src/video/anime4kWebgpu.ts`：rgba32float 中间纹理、最近邻采样、按引用计数回收中间纹理、逐趟追踪、编译信息与回读接口 | Electron 实测：192×192 单帧 4.2–4.7ms |
| VQ-57e | 验收台 `e2e/webgpu-enhance-probe` + 门禁 `e2e/webgpu-enhance.test.cjs`：真实 Electron 里对同一张输入图跑 WebGPU 与原 WebGL 两条链路，逐像素比对 | `node --test e2e/webgpu-enhance.test.cjs` 通过 |

**本轮的关键事实**：

- 原链路的执行顺序是「先 MAIN 链、再 PREKERNEL 链」：`Restore_CNN_S` 与 `Upscale_CNN_x2_S` 的 `hook_PREKERNEL` 是空实现，而 `Clamp_Highlights` 的会真的再跑三趟，因此可见结果是 `clamp(restore(clamp(输入)))`。
- WebGPU 路径已编译零错误、超分档零未捕获错误；中间纹理精度（fp16 → fp32）与采样器（线性 → 最近邻）都不改变 8 位输出，说明**残余差异是结构性的，不是数值精度**。

**未完成（不得当作已达成）**：

1. **输出尚未与原链路逐像素一致**：实测平均差 9.24/255（均衡）、18.27/255（超分），超阈值（>16）通道占比 11%/28%。按 VQ-28「链路不同即视为质量退化」，因此**没有接进播放器**，WebGL 仍是唯一生效路径，用户可见行为不变。
2. 「性能」档（Deblur_DoG）与「锐化」档（Restore_CNN_M 收尾趟引用中间变量）尚未覆盖，计划函数对它们返回 `null` 并回退。
3. 未接入的其余部分：把增强结果交给补帧渲染器需要的纹理交接（WebGPU 输出 → canvas → WebGL 纹理）还没做。

**下一步**：用 `e2e/webgpu-enhance-probe` 逐趟二分定位结构性差异（先比 clamp 单段，再比 restore 单段），把平均差压到 0；然后才做纹理交接与接入。

**VQ-45（2026-09-22）：用户反馈「你修改后画面波动非常大」，本轮为回归修正。** 四处根因与处置见[播放器设计](./media-player-development.md) P13 修正节：不匹配格点不再以 0 置信度输出（改为全局平移 + 0.5 置信度，避免渲染着色器退回硬切换原帧）、歧义判据由"次优解代价差"改为局部对比度、平移先验步长 2→1 并加有界采样、分析尺寸变化时重置运动历史。**默认后端回退为 CPU**；WebGPU 通过 `VITE_FLOW_BACKEND=webgpu` 或 Worker URL 的 `?sanyeFlowBackend=webgpu` 显式启用。

用户「换一个为实时设计的轻量模型，用这个进行实现吧」。目标是把每源帧的 14–20ms CPU 运动估计换成 GPU 常驻计算，为实时补帧留出余量。实现、取舍与实测见[播放器设计](./media-player-development.md) P13 与[测试报告](./media-player-test-report.md)。

**关于"轻量模型"的边界（必须先说明）**：本轮落地的是**为实时设计的轻量算法管线**（三层金字塔块匹配 + 逐级细化 + 全局平移先验），不是预训练的神经网络。原因是本机与仓库都没有可用的、许可已核对的权重来源；凭空引入来路不明的权重会同时破坏本项目的资产摘要核对与第三方许可记录。因此这里选择了一条不需要权重、也不增加包体积的实时路径。若后续要换成真正的轻量神经网络，需要先确定权重来源与许可，再按 VQ-10 的流程走一遍。

每次原始证据保存在 `sanye_deploy/.local/player-quality/<运行标识>/`，包含环境摘要、源码状态、参数、逐窗口数据、截图/片段、错误和结论。P0 工具入口及实际覆盖范围见[播放器测试报告](./media-player-test-report.md)，目录存在本身不代表阶段验收通过。对外发布证据前检查媒体授权及私人路径，仓库只保存可复核摘要和索引，不提交大体积媒体或私有片源 URL。

阶段交付必须同步设计、测试计划和专项报告；正式任务状态回写任务清单。默认行为、依赖、桌面交付变化再按[文档变更规则](./document-change-rules.md)同步相应唯一事实源，不借文档计划扩展实现范围。

## 7. 决策、风险与回滚

| 风险或缺口 | 处理与退出条件 |
| --- | --- |
| 真实样本/设备不足 | 继续完成独立可执行的代码与合成验证，缺失项目标记待环境并列出所需样本或设备；不写成全面通过 |
| 更强模型质量或性能不达标 | P3 停止默认接入；保留现有光流和小型 Anime4K，以数据记录结论 |
| 刷新回调不交付或计时器分辨率不足 | 刷新时钟先确认实际交付，未确认时回退截止时间计时器；生成帧增加但实际呈现无收益时不得视为成功优化 |
| 起播高档记忆失效（换网、限速、CDN 换线） | 已实现：记忆条目带有效期与失败作废，首片超时或失败回落低档；用户清除偏好后按默认低档起步 |
| 增强档位恢复造成振荡 | 已实现：恢复需要 5 秒冷却与 3 秒稳定样本门槛，恢复后 20 秒内再次降档按恢复失败把冷却翻倍（上限 60 秒）；结构性限制与 240 FPS 平衡直接锁定可恢复上限，只保留降档 |
| 移入 Worker 的增强改变像素输出 | 已实现：主线程与 Worker 共用同一条档位链路，同源同尺寸五档 RGB 逐字节一致；`enhancementPath: 'main'` 保留原主线程路径作为对照与回退，代价是主线程重新承担逐帧增强 |
| 自适应收缩导致补帧窗口余量不足 | 已实现：目标越过最新源帧（画面正在重复同一帧）时按实测需要恢复一步（40ms、1 秒冷却、上限 150ms），恢复只出现在已经停顿的窗口并单独计数；连续干净窗口有余量时才收缩，`interpolationDelay: 'fixed'` 可一键回到固定 150ms |
| 设备配置缓存过时 | 使缓存失效并重新探测；默认可回到现有保守档，不阻断原始播放 |
| 原生模块破坏兼容或扩大包体积 | 候选阶段单独比较包体积与加载条件；未通过包内验收不进入默认发行路径 |
| 画面更锐但损坏细节 | 使用逐场景对照和时间一致性门禁，拒绝仅依赖清晰度主观印象的升级 |

执行时为本轮修改保留可复现基线和逐项差异，不将未提交工作区等同于单个提交。实验算法应能独立停用；运行异常优先回到现有补帧或原始视频。交付回滚使用已验证的旧包与兼容配置，保留用户数据，不依赖破坏性清理恢复现场。
